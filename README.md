# Chess Upping

A personal chess-improvement app. Sign in with Google, connect a Lichess
account, and the app downloads every standard game you have played, keeps a
copy in your browser, and lets you explore your own games like an opening
book, in the style of openingtree.com.

Live site: https://chess-upping.web.app

## How it works

- **Angular 22** (standalone components, signals, zoneless) with Angular Material.
- **Firebase Auth** (Google) identifies users. **Firestore** holds a private
  `users/{uid}` document per user and one shared, public `games` collection.
  The document id of a game is its Lichess id, so a game played between two
  users of the app is stored once.
- **Lichess OAuth (PKCE)** runs entirely in the browser. No app registration or
  client secret is needed. The token is kept on the user's own profile document,
  readable only by that user, so a link made on one device works on all.
- **Local first.** Games live in IndexedDB (via Dexie). Every screen reads from
  memory and IndexedDB; the network is only used to sync. A sync pulls games
  uploaded to Firestore since the last pull, streams games from Lichess at
  60 games/second starting a little before the newest one already downloaded
  (so games that finished late are still caught), saves them locally, then
  uploads them to Firestore in batches. Anything not uploaded (quota, offline)
  is retried next time; games the server refuses because the opponent already
  uploaded them are simply marked done.
- **Opening tree.** Games are filtered by colour, result, time control,
  rated/casual, period and opponent rating, then aggregated at each node
  either by the position reached (merging transpositions, using a per-game
  position index kept in IndexedDB) or by exact move order: game counts,
  win/draw/loss, engine eval of the resulting position, average thinking
  time, average opponent rating, last played, and the games that reached the
  position. Opening names come from the ECO dataset keyed by position
  (`public/openings.json`, generated by `scripts/build-openings.mjs` from
  lichess-org/chess-openings). The position can be compared with the Lichess
  masters database or player pool through the public opening explorer.
- **Engine analysis.** Stockfish 19 (the lite, single-threaded WebAssembly
  build, no cross-origin isolation needed) runs in a pool of Web Workers.
  Evaluations are keyed by position (FEN without move counters) in a local
  table mirrored to the shared `positions` collection, where a record is only
  ever replaced by a deeper one. The game viewer shows the eval after every
  move, the opening tree shows the eval of the position on the board, and the
  Engine page evaluates every game you played in the background, resuming
  where it stopped. Lookups go local store, then cloud, then engine, so a
  position is never searched twice.
- **Study.** The game viewer judges every move from the stored evaluations
  (inaccuracy ?!, mistake ?, blunder ??, with an accuracy figure and an eval
  graph). The Mistakes page gathers them across all games, grouped by opening
  and by repeated position, each linking back to the game at that move or to
  the explorer at that line. Drills turn the user's habitual moves into
  spaced-repetition cards (slowest first) and the positions from the Mistakes
  page into cards where the moves actually played are refused. Any answer
  that costs less than an inaccuracy by the engine's evaluation is accepted;
  the grader looks the two positions up in the evaluation table and only
  searches when they are new. Sequence mode plays the opponent's reply
  automatically (the most common one from the user's games for repertoire
  cards, the engine's line for mistakes) for up to three moves. Progress
  lives under the user's private `drills` subcollection. Private notes can be
  kept on any position or game (`users/{uid}/notes`); the explorer, the game
  viewer and the drill page all show the same note box, so a lesson learnt in
  a drill can be written down on the spot. The drill page steps back and
  forth through its moves (arrows, Home and End, or the move list), and
  through the moves that led to the drill position when every game reached
  it by the same move order; a position reached by several move orders stops
  the history there, and says so.
- **Live engine.** Every board (explorer, game viewer, drills) has an engine
  switch and a choice of one to five lines. A dedicated Stockfish worker keeps
  analysing the position on screen and streams its principal variations;
  clicking the first move of a line plays it. The viewer lets you play moves
  on the board to explore a variation from any point of the game, and drills
  allow free exploration after an answer.
- **Keep awake.** While the engine, a Lichess download or an upload is
  running, the app holds a Screen Wake Lock so the computer does not go to
  sleep (a switch on the Engine page turns this off). The lock only works
  while the tab is visible and cannot stop a closed laptop lid from sleeping.
- **Firebase config** is never committed. The app fetches it at runtime from
  Hosting's reserved `/__/firebase/init.json`.

## Project layout

```
src/app/core/firebase     Firebase initialisation from init.json (and emulators)
src/app/core/auth         Google sign-in, route guard, user profile document
src/app/core/lichess      OAuth PKCE, Lichess API client, NDJSON game parsing
src/app/core/data         IndexedDB store, Firestore games repository, sync
src/app/core/engine       Stockfish worker wrapper, UCI parsing, worker pool
src/app/features          Pages: opening tree, game viewer, mistakes, drills, engine, login, callback
firestore.rules           Security rules; firestore.indexes.json the composite index
.github/workflows         CI, preview channels on PRs, live deploy on main
docs/BACKLOG.md           Features to build next
```

## Development

Requires Node 24.

```sh
npm install
npm start          # ng serve on http://localhost:4200
```

`npm start` proxies `/__/firebase/init.json` to the production Hosting site
(see `proxy.conf.json`), so the dev server talks to the real project. Google
sign-in works on localhost because Firebase authorizes it by default.

To work fully offline against the Firebase emulators instead:

```sh
npm run build
npx firebase emulators:start   # app on http://localhost:5000
```

When the app runs on localhost and finds the Emulator Hub on port 4400, it
connects Auth and Firestore to the running emulators automatically (this also
applies to `npm start` while the emulators are up). This needs Java for the Firestore emulator and credentials that can read the
project's web app config (`GOOGLE_APPLICATION_CREDENTIALS` pointing at a
service account key, or `firebase login`).

The toolbar shows the short commit hash of the running build. It comes from
`src/app/version.generated.ts`, written by `scripts/write-version.mjs` before
every build, serve and test run (the file is not committed).

Other scripts:

```sh
npm test               # unit tests (vitest)
npm run format         # prettier
npm run build          # production build into dist/chess-upping/browser
```

## Deployment

Pushing to `main` runs `.github/workflows/deploy.yml`, which deploys Firestore
rules and indexes, then Hosting. Pull requests get a temporary preview channel
(`.github/workflows/preview.yml`). Both use the
`FIREBASE_SERVICE_ACCOUNT_CHESS_UPPING` repository secret.

The service account needs these IAM roles on the project for the workflows
to succeed (the default `firebase-adminsdk` account has only some of them):

- Firebase Hosting Admin (`roles/firebasehosting.admin`)
- Firebase Rules Admin (`roles/firebaserules.admin`)
- Cloud Datastore Index Admin (`roles/datastore.indexAdmin`)
- Service Usage Consumer (`roles/serviceusage.serviceUsageConsumer`)

Granting the broader Firebase Admin role (`roles/firebase.admin`) also works.
Without the index role, the composite index in `firestore.indexes.json` can
be created by hand in the Firebase console; the app still works without it
but cannot pull games uploaded from other devices.

Google sign-in only works on domains listed under Authentication > Settings >
Authorized domains in the Firebase console. `chess-upping.web.app`,
`chess-upping.firebaseapp.com` and `localhost` are there by default; a preview
channel host has to be added by hand if you want to sign in on it.

## Data model

`users/{uid}` (private to the user)

```
email, displayName, updatedAt
lichess: { id, username, token, linkedAt }
```

`games/{lichessGameId}` (public, readable by any signed-in user)

```
id, rated, variant ('standard'), speed, perf, createdAt, lastMoveAt, status,
winner ('white' | 'black' | null), players [lichess ids of the human players],
white { name, id, rating, ratingDiff }, black { ... },
moves 'e4 e5 Nf3 ...', opening { eco, name, ply } | null,
clock { initial, increment } | null, source,
uploadedBy (uid), uploadedAt (server timestamp)
```

`positions/{key}` (public; key = FEN without move counters, `/` replaced by `_`)

```
key, fen, cp | null, mate | null (White's point of view), depth, bestMove,
pv (UCI, up to ten moves), engine, nodes, evaluatedAt, uploadedBy, uploadedAt
```

A game document is created once, by a signed-in user, with a strictly checked
shape, and is never updated or deleted. A position document may be replaced
only by a deeper evaluation. The incremental pull on other devices
pages on `uploadedAt`, so documents arriving out of date order are not missed.
Because the Lichess link is made client-side, the rules cannot prove that the
uploader played the game; see the backlog for server-side verification.

The rules have their own tests, run against the Firestore emulator:

```sh
npm run rules:test
```
